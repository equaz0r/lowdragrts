## What This Is
A heightmap-based real-time strategy game inspired by Total Annihilation. Built with TypeScript, Three.js, and Webpack. Rendered in the browser. Hobby project — worked on in sessions when time allows.

### Gotcha: don't switch `moduleResolution` to `"bundler"`
Tried this while debugging a `postprocessing` type-resolution issue — it broke `three/examples/jsm/...` subpath imports (OrbitControls) and did NOT fix the actual problem. The real fix was deleting a stale hand-written `src/types/postprocessing.d.ts` stub that was shadowing the real package's bundled types. Keep `"node"`.

### Gotcha: `npm start`'s dev server can silently serve a stale bundle (OneDrive)
This repo lives in a OneDrive-synced folder. Webpack's default file watcher relies on native OS fs-change events, which OneDrive's sync layer can drop or delay — the dev server then keeps serving the pre-edit bundle with no error, no warning, and (since nothing rebuilt) no live-reload refresh either. Symptom: a code change that should be visible in the browser "does nothing" / "looks exactly the same as before" even after a manual refresh. Fixed 11 Aug 2026 by adding `watchOptions: { poll: 1000 }` to `webpack.config.js` (slower — checks every 1s instead of relying on native events — but actually reliable here). If an edit ever again seems to have zero effect in the browser, restart `npm start` fresh first before assuming the change itself is wrong.

### World Dimensions
- Total size: **8,000 × 8,000** world units, `GridParameters.CELL_SIZE = 64`
- **Render mesh divisions = grid cell count (125), deliberately equal** — 1 mesh quad = 1 grid cell exactly, so `TerrainGrid.ts`'s lines sit on real mesh vertices with zero approximation gap. (Was 200 divisions/40-unit segments, denser than the grid — that mismatch was the root cause of the grid/terrain-tile misalignment bug fixed this session. Don't decouple these again without a good reason.)
- Terrain height: 0–1400 units default (`HEIGHT_SCALE` in `TerrainConfig`)
- Camera starts at (4000, 3000, 4000), looking at origin, far clip 500000 (see `CameraConfig.ts` comment for why — LightingSystem's sky/halo geometry needs the headroom)
- Orbit range: 100–16,000 units
- Building footprints: `BuildingFootprints.SMALL/MEDIUM/LARGE` = 1/2/3 grid cells = 64/128/192 world units (convention only — no real buildings yet)

Verified with a standalone noise sweep (not just theorized): clean, large, coherent zones. On by default (`regionMaskEnabled`), off in the Rolling preset.

- ✅ Terrain reflection shader — tinted by the sun's actual live colour now (was hardcoded near-white)

- ✅ Bloom/tone-mapping/grading pipeline (`postprocessing` package) — HDR buffer, ACES tone mapping, brightness/contrast + vignette grading pass
- ✅ HeightMap — bilinear height query, surface normals, slope, traversability, ground orientation, flying altitude, `isInBounds`, `isBuildable`
- ✅ Terrain presets — `PRESET_DRAMATIC` / `PRESET_ROLLING` / `PRESET_BATTLEFIELD`
- ✅ OrbitControls camera, TerrainControls (full shape/region/valley/plateau exposure), EdgeControls, ReflectionControls
- ✅ **Save/load settings** (`SettingsIO.ts`) — Export writes the whole scene (terrain shape, seed, grid colours/pulse, reflection/sun) as JSON into a textarea + best-effort clipboard copy; paste JSON back + Import restores it exactly, including the seed (regenerates with the SAVED seed, not a new random one)
- ✅ **Draggable panels** (`Draggable.ts`) — all 5 debug panels (Terrain Shape, Grid Appearance, Terrain Controls, Save/Load Settings, Performance) reposition by dragging their title bar; position persists in `localStorage` across reloads. "Reset Panel Positions" button (in the Save/Load Settings panel) clears saved positions + reloads.
- ✅ **"Sea" shimmer** (`TerrainMaterial.ts`) — low/flat ground gets a cheap time-varying normal perturbation for the reflection calculation only (not the real geometric normal), so glints dance like light on water even though the mesh never moves. Not real waves — see `## Water / Sea — future options` below for what a fuller version would take and why it wasn't done now. Gate is `height / heightScale` (matches the vertex-colour gradient's own normalisation) — NOT a fraction of this generation's actual min/max height, which is a different, less reliable thing (see the comment above `SEA_LEVEL_FRACTION` in the source — got this wrong on the first attempt, a min/max-relative threshold missed the visible sea entirely because an unrelated outlier elsewhere skewed the range).
- ✅ **Sun glitter path — explicitly authored wedge envelope + noise texture, verified by simulation before shipping** (`TerrainMaterial.ts`, 11 Aug 2026, third rewrite) — two earlier attempts both failed for real, findable reasons, not just "wrong numbers": (1) a screen-space camera↔sun alignment hack could only ever produce a single small blob; (2) jittering the terrain normal before a Blinn-Phong test, hoping the wedge would emerge on its own from the geometry, was SHIPPED with that "let it emerge" reasoning documented as deliberate — but Simon's follow-up screenshots (flat land, bright low sun) showed it clearly wasn't working, and this time, instead of reasoning it through by hand again, wrote a standalone Node simulation of the actual shader math (`calculateSunGlitter()` translated to JS, real camera/sun positions, screen-space raycasting matching how a fragment shader actually samples) — kept as `tools/simulate-sun-glitter.js`, `node tools/simulate-sun-glitter.js` to re-run it. That **proved** attempt 2 produces the shape backwards for this game's specific camera/sun geometry (wide near the camera, narrow near the horizon) — confirming the "just let it emerge" assumption was wrong for this engine, not merely under-tuned. The same simulation caught a second, independent real bug: `facingSun = dot(normal, sunDir)` was being used as a continuous brightness DIMMER — correct for diffuse/Lambertian light, wrong for this SPECULAR effect, since real mirror-like reflection gets STRONGER at grazing/low-sun angles (Fresnel), not weaker. That dimmer was crushing brightness exactly when the sun is low and large — the literal symptom Simon reported ("as the sun gets bigger, the reflection is less and less right"). Fix, verified in the simulation to produce the correct wide-at-horizon/narrow-at-camera shape before touching real code: `calculateSunGlitter()` now explicitly computes the camera→sun ground axis (from the real live `cameraPosition`/`sunWorldPosition`, not an arbitrary mask) and builds a wedge envelope along it — narrow near the camera (`GLITTER_WIDTH_NEAR`/`ALONG_NEAR`), wide near the horizon (`GLITTER_WIDTH_FAR`/`ALONG_FAR`) — then textures that envelope with animated hash noise (`GLITTER_FREQUENCY`/`SPEED`/`SPARKLE_CONTRAST`) for sparkle, with a `GLITTER_BASE_GLOW` floor so the shape stays visible even where noise happens to be dim. `facingSun` is now a soft on/off gate (`smoothstep`), not a multiplier. Still generic (world position, normal, sun position, camera position, time only — no terrain-specific state), reusable for buildings/units later per Simon's forward-compat note. `ReflectionParameters.SUN_GLITTER_WEIGHT` (1.1) is the only tunable in the weighted-sum config; the rest live locally in `TerrainMaterial.ts`. Numbers are first-pass but shape-verified by simulation, not guessed — still not visually confirmed in the actual browser, check this first next session.
- ✅ **Sun glitter reach/width are now live sliders** (`ReflectionControls`'s "Sun Glitter" section, 11 Aug 2026 round 4) — the wedge's axis maths was verified correct (converges exactly on the sun's true screen position — checked numerically for an off-axis camera too, see `tools/simulate-sun-glitter.js`), but Simon reported it still read as a thin, slightly-misaligned LINE. Root cause, also found by simulation: that axis only converges on the sun in the FAR limit; the NEAR-camera segment — the part actually visible on screen — is genuinely offset from dead-centre-on-the-sun for any camera not looking directly along that axis. That's correct geometry for a thin line, not a bug, but a thin line makes the imprecision obvious, while a wide patch (like real photographed sun glitter) reads as "in the sun's direction" regardless of pixel-perfect alignment. Fixed the defaults to reach full width much sooner (`GLITTER_ALONG_FAR` 6000→2500, `GLITTER_WIDTH_POWER` 1.4→0.8 for fast early growth, `GLITTER_WIDTH_NEAR` 50→70) — but also promoted reach (`GLITTER_ALONG_FAR`) and width (`GLITTER_WIDTH_FAR`) to a live `glitterReach` uniform with real-time sliders, since the "right" reach/width fundamentally depends on Simon's actual play-camera distance, which he can now dial in directly instead of another guess-and-ship round-trip. Included in `SettingsIO` export/import (`ReflectionSettings.glitterReach`/`glitterWidth`, with a safe fallback for older saved exports missing the fields).
- ✅ **Per-fragment view direction fix** — the OTHER half of the misalignment bug, and the bigger one: `cameraDirection` was `normalize(camera.position)` — direction from the WORLD ORIGIN to the camera, a single vector reused for every fragment on the entire 8000-unit map. Only correct for fragments actually at the origin; everywhere else wrong, worse the further off-centre or the further a fragment was from the origin (exactly "aligns only looking straight down the middle"). Fixed to the correct per-fragment `normalize(cameraPosition - vWorldPosition)`. Uses Three's own built-in `cameraPosition` uniform (declared by `#include <common>`, auto-updated every frame) rather than a custom one — **don't declare a uniform named `cameraPosition` yourself in a Three.js material, it's already provided and redeclaring it is a GLSL compile error.**
- ✅ Noise visualiser at `/noise-visualizer.html`, performance monitor, buffer pooling

## Active Tuning Notes (review at session start)

### Sun (LightingSystem.ts) — known things to revisit
- Sun is a **flat billboarded `CircleGeometry`**, not a sphere — deliberate. A 3D sphere's surface has real depth (bulges toward camera), so under perspective projection any pattern on it (scanlines, colour bands) still curves slightly even when built from "flat" 3D quantities. A flat billboard (same technique as the halo) has none of that. If the sun ever needs to go back to a sphere for some 3D-lighting reason, expect scanlines/gradient to need rework.
- Scanlines: upper half only, fade in via `smoothstep(0.0, 0.18, upperT)` from the equator (a hard on/off switch there read as lines abruptly stopping). Density/thickness: packed tight + thick near the equator, sparse + thin near the pole (`pow(upperT, 0.4)` warp).
- Minimum sun position was computed, not guessed: at its lowest setting the sun used to sit at **world Y=-865 — below the horizon plane**. Fixed via the hardcoded `minAngle` constant in `updateSunPosition()` (now gives Y=+350). If `SUN_MIN_HEIGHT`/`SUN_MAX_HEIGHT` config values are ever changed expecting the sun's vertical range to move, note that those only affect the *normalization* of the height slider — the actual min/max angle constants are separate hardcoded values in the same method and don't derive from that config.
- `SUN_TERRAIN_LIGHT_SCALE` (LightingConfig) decouples the sun's own visual brightness (disc/halo opacity) from how much light it actually casts on terrain — these used to be the same number by coincidence, not design. Also: the "Sun Intensity" slider's effect on terrain lighting is dead code in practice (an early assignment in `updateSunPosition()` gets overwritten later in the same method by a purely elevation-based calculation) — only sun height/elevation actually drives terrain light intensity.

### Reflection shader (TerrainMaterial.ts) — known things to revisit
- **"Debug: Glitter Only" checkbox** (bottom of `ReflectionControls`, 11 Aug 2026) — shows `calculateSunGlitter()`'s raw output in isolation (flat greyscale, roughness/metalness forced non-reflective so Three's built-in specular can't contribute). Use this FIRST whenever it's unclear whether a reflection complaint is about the sun-tracking term itself or one of the other confounds (ambient weighted-sum terms, Three's built-in specular) — it would have saved several rounds this session if it had existed from the start. **Writes directly to `gl_FragColor` at `#include <dithering_fragment>` (the LAST chunk in Three's fragment shader, verified against the installed package source)** — NOT to `diffuseColor` earlier in the pipeline, which is only lighting INPUT and still gets multiplied by scene light intensity before reaching the screen (first version of this tool had exactly that bug — showed flat black in a dim scene regardless of the real value, which almost caused a false "sunGlitter is broken" conclusion). Note the neon grid lines are `EdgeMaterial` — a completely separate mesh/material — and are NOT hidden by this toggle; judge the debug view by the terrain SURFACE colour between grid lines, not the lines themselves.
- **The real culprit (11 Aug 2026, round 9): THREE.JS'S OWN BUILT-IN PBR SPECULAR HIGHLIGHT, not any of my custom shader code at all.** Cutting the 4 weighted terms below (round 8) made no visible difference — because `calculateReflection()` only feeds `diffuseColor`/`roughnessFactor`/`metalnessFactor` INTO Three's standard lighting; the actual specular highlight computation is Three's own built-in code, reacting to the real `sunLight` `DirectionalLight`, completely separate from anything in this file's `onBeforeCompile` injection. At the old baseline `REFLECTION_PARAMS` (metalness 0.61, roughness 0.47) the material was glossy enough for Three's standard PBR to produce a real, physically-correct specular highlight ALL ON ITS OWN — the exact same "smooth surface → single point, misaligned off-axis" issue solved for the custom `sunGlitter` term at the very start of this session, except this one was never touched by any of that work, since it's not my code. This was almost certainly the actual "reflection that doesn't track the sun" Simon had been reporting the ENTIRE session, underneath everything else — confirmed empirically, not just theorised: setting the Roughness slider to 1.0 live made the mystery streak disappear entirely. Fixed by raising baseline roughness/lowering baseline metalness in `REFLECTION_PARAMS` (0.61/0.47 → 0.1/0.88) — because `mix(baseline, 0.1, reflectionStrength)` only changes where `reflectionStrength` is LOW, this doesn't reduce shininess inside the `sunGlitter` wedge at all, it just stops the WHOLE TERRAIN being glossy by default. **If reflections ever look "shiny everywhere, ignoring my shader logic" again, check `REFLECTION_PARAMS.x`/`.y` (the Metalness/Roughness sliders' baseline) before assuming the custom weighted-sum code is broken — Three's own built-in lighting is a real, separate system this project has never explicitly designed around before now.**
- **The visible "reflection" is 4 separate additive terms, and only ONE of them (`sunGlitter`) has ever read the sun's position** (validated 11 Aug 2026, round 8, by reading the shader directly — not assumed): `positionFactor` (hardcoded "west is shinier", never reads `sunWorldPosition`, and at low slider values is a flat CONSTANT across the whole map, not even a gradient), `panelFactor` (pure per-100-unit-grid-cell texture noise), and `grazingFactor * heightFactor` (camera-viewing-angle vs. terrain slope — zero on flat ground, up to full weight on grazing views of mountains/cliffs, and visibly SHIFTS as the camera orbits since it's camera-relative, which is very easy to mistake for sun-tracking). At their old weights these three were routinely OUTSHINING `sunGlitter` (weight 1.1, but its typical value is much lower than 1.0 in practice — see `GLITTER_BASE_GLOW`). This is almost certainly what Simon had actually been reacting to for the entire multi-round sun-glint saga earlier in this session — every fix to the sun-tracking term left the DOMINANT visible effect unchanged, because that dominant effect was never sun-tracking in the first place. Cut `POSITION_FACTOR_WEIGHT`/`PANEL_FACTOR_WEIGHT`/`GRAZING_FACTOR_WEIGHT` roughly 4-5x (0.15/0.08/0.32 → 0.04/0.02/0.06) per Simon's explicit choice ("cut them back hard") so they read as a subtle base sheen and `sunGlitter` is unambiguously the dominant, obviously sun-tracking visual. **If a future reflection complaint doesn't visibly change after editing `calculateSunGlitter()`, check these three terms' contribution before assuming the sun-tracking code is still wrong** — this exact confusion cost multiple rounds once already.
- **Sun glitter is an explicitly authored wedge envelope now, not emergent physics** (see What's Working above) — `calculateSunGlitter()`, generic/reusable, not terrain-specific. If a reflection complaint comes in, check which system it actually is first: wrong SHAPE/SPREAD (too pinpoint, too wide, wrong side of the sun, wrong end narrow) → this glitter code (`GLITTER_ALONG_NEAR`/`ALONG_FAR`/`WIDTH_NEAR`/`WIDTH_FAR`/`WIDTH_POWER` for the envelope shape, `FREQUENCY`/`SPEED`/`SPARKLE_CONTRAST`/`BASE_GLOW` for the sparkle texture, `SUN_GLITTER_WEIGHT` in `ReflectionParameters` for overall contribution); too bright/dim/rare in general → the weighted-sum/clamp system below, which is unchanged and separate.
- **Two failed prior approaches, don't repeat either, and don't go back to "let it emerge" without re-running the simulation first**: (1) comparing camera→fragment vs camera→sun screen-space direction — can only ever produce a small aligned blob, never a spread; (2) jittering the terrain normal before a Blinn-Phong test against the real sun/view directions, on the theory that the wedge shape would emerge naturally from grazing-angle optics (real Cox-Munk wave physics, correctly reasoned about in the abstract) — this one SHIPPED on that reasoning, but a follow-up numeric simulation (world math translated to JS, screen-space raycast sampling — `tools/simulate-sun-glitter.js`) proved it produces the shape BACKWARDS for this game's specific camera/sun geometry (wide near camera, narrow near horizon) — the general Cox-Munk argument doesn't automatically transfer to this engine's specific fixed sun-orbit geometry. If tempted to try "pure emergent" again, simulate first — don't just re-reason through it, that already failed once.
- **`facingSun`/`dot(normal, sunDir)` must be a GATE, not a brightness multiplier**, for any specular/mirror-style effect — that's Lambertian diffuse-lighting math (correct for how MUCH light lands on a surface) applied to a specular/reflective effect (which should get STRONGER at grazing/low angles — Fresnel — not weaker). Using it as a multiplier silently crushed the whole glitter effect exactly when the sun was low/large, which is why "as the sun gets bigger the reflection is less and less right" was a real, measurable bug, not a subjective impression. Found via the same simulation, not visually. If a future specular-style effect dims unexpectedly at grazing angles, check for this exact mistake first.
- Envelope constants (`GLITTER_ALONG_NEAR=250`/`WIDTH_NEAR=70`/`WIDTH_POWER=0.8`) were chosen by simulating the actual camera frustum (not guessed) — `ALONG_NEAR` isn't 0 because for most camera angles the ground at the camera's own feet isn't even in the view frustum, so tuning it to 0 wastes the tightest part of the taper somewhere off-screen. If the near end looks wrong for typical play camera angles, re-run the simulation rather than eyeballing — that's what caught the backwards-shape bug earlier that eyeballing wouldn't have. `ALONG_FAR` is the `glitterReach.x` uniform's live-adjustable default (2500, slider range 500-12000) — retune with the "Sun Glitter" panel in-game first, not by editing the constant, unless changing what a fresh load starts with.
- **Far-end width auto-scales with the sun's apparent size, NOT a flat constant** (12 Aug 2026, round 17) — `mix(GLITTER_WIDTH_AUTO_MIN, GLITTER_WIDTH_AUTO_MAX, pow(1-sunHeightT, GLITTER_WIDTH_CURVE_POWER))`, fit against 4 example points Simon gave (exact at both endpoints, ~10% off on the two middle ones — verify/retune via `tools/simulate-sun-glitter.js`'s built-in curve check before hand-tuning blind). The "Glitter Width" slider (now labelled "Glitter Width ×" in the UI) is a MULTIPLIER on this curve (default 1.0, range 0.2-3.0), not an absolute width any more — `glitterReach.y` in the shader. Settings-file imports from before this change would have an absolute-width value (200-3000 range) in that slot; `ReflectionControls.importSettings()` clamps it into the new 0.2-3.0 range so an old save degrades gracefully instead of blowing the curve out.
- **Wedge falloff is now a single gradient from the centreline, not a flat-then-cliff** — `smoothstep(0.0, allowedWidth, lateralOffset)`, was `smoothstep(allowedWidth*0.5, allowedWidth, ...)` (fully bright inner half, fade only in the outer half). Gives the "central bright core, soft edge" look — if a future request wants MORE of a plateau (flatter centre, sharper edge) rather than a pure gradient, that's the lever to reconsider, not the width values.
- **Individual shards have their own radial glow now** (`GLITTER_SHARD_GLOW_FLOOR`) — brightest at each shard's own centre, fading toward its edges, layered on top of the seam border. This is what's carrying "looks like a glint, not painted-on colour" — a flat-brightness shard reads as a coloured rectangle regardless of how bright it is; a centre-to-edge falloff reads as a small highlight. If glints ever look flat again, check this hasn't been simplified away before assuming it's a brightness/colour problem.
- **`REFLECTION_PARAMS`/`SUN_BASE_INTENSITY` are Simon's confirmed-good combination** (12 Aug 2026, round 18) — metalness 1.00, roughness 0.32, positionFactor 2.70, reflectionPower 1.50, sun intensity 2.00, called "the perfect combination for the effect I need across the range." Sun Height/Glitter Reach/Glitter Width are deliberately NOT part of this — those stay scene-dependent, adjust per shot. Don't retune these five without a specific reason; if reflections look wrong, suspect something else first (there's a long history of that in this file).
- **`GLINT_LOW_SUN_BOOST_MAX`/`POWER`** compensate for the width curve above spreading the same sparkle density over more area at low sun heights — steeply concentrated near `sunHeightT=0` (full 2x boost only at Sun Height -0.80, ~1.3x at -0.56, negligible above ~-0.3). First-pass numbers tuned to Simon's stated boundary, not exhaustively verified — if the "needs to be brighter at low sun" complaint resurfaces, this is the first place to check before assuming something else broke.
- **Sparkle texture is flat per-cell shards, GRID-ALIGNED to the real neon grid, and NOT time-animated** (12 Aug 2026, three rounds) — `calculateSunGlitter()` floors a `GridParameters.CELL_SIZE`-sized, grid-origin-aligned coordinate before hashing (`GLITTER_SHARD_SIZE`, same `+mapSize/2` half-offset `GridSystem.worldToCell()` uses) — same floor-before-hash TECHNIQUE as `getPanelFactor()`, but deliberately snapped to the SAME cells as the visible grid, not an arbitrary independent size. `GLITTER_SHARD_SEAM` is the dark border width between shards (cell-fraction units, 0-0.5). Brightness is a pure function of `shardCell` position — no `time` input at all; it still changes correctly as the camera/sun move (via `wedgeFactor`/`facingSunGate`, both live-position-dependent), but sits perfectly still on a static view. Three failure modes to never repeat: (1) continuous (non-floored) hash → reads as TV static; (2) floored but at an arbitrary size/using a scrolling coordinate → floored shards that visibly don't match the real grid ("looks projected on top of it"); (3) floored+aligned but with ANY time input feeding the hash (even a quantized "re-roll every N seconds" step, tried and reverted in round 13) → unmotivated flicker on a completely static camera/sun.
- **`gridSize` uniform: set from JS since this file's first version, never actually declared in GLSL until 12 Aug 2026** — same "JS object has a value, no matching `uniform` line in the shader source, GPU never receives it" mistake as `time`'s documented history above. Nothing needed to read `gridSize` until the shard-grid-alignment fix, so it went unnoticed. If a new uniform seems to have no effect, check it's actually `uniform ... name;` declared in the injected GLSL common block, not just set in the JS `s.uniforms` object — this has now happened twice in this file.
- **Alignment vs. width is a real tradeoff, not a bug to "fully fix"** — the wedge's axis is verified to converge exactly on the sun's true screen position in the far limit, but the near-camera segment (what's actually visible) is genuinely offset from dead-centre for any camera not looking directly at the sun. Chasing perfect alignment there is chasing something that isn't geometrically true for a thin line; the fix is width (a wide patch reads as "in the sun's direction" even when imprecise, the way real photographed sun glitter does), not more precision. If a future report says "still not quite lined up" after the wedge is already visibly wide, that's expected/acceptable — don't over-invest in pixel-perfect near-camera alignment.
- `calculateReflection()`'s `reflectionStrength` is now `clamp()`-ed to `[0,1]` — it used to be unclamped and routinely exceeded 1.0 (measured ~91% of realistic viewing angles before the fix), which fed three separate `mix()` calls as an unclamped blend factor and caused extrapolation artifacts (negative roughness, metalness >1, blown-out colour). This was the actual root cause of a "way too bright/shiny" complaint that survived several rounds of tuning metalness/roughness/sun — those inputs were being blown past, not respected. If reflections ever look broken again, check this clamp survived before re-tuning weights.
- `smoothstep(0.0, max(0.001, reflectionParams.z), ...)` — the `max()` guard matters. `reflectionParams.z` (Position Factor) reaching exactly 0 is undefined GLSL behaviour (`smoothstep` divide-by-zero) and produced a NaN/white-blowout bug. The UI slider's own minimum is also raised to 0.1 for the same reason — don't lower it back to 0.
- `ReflectionParameters` weights are data-driven, not guessed — simulated the exact shader formula in Node across 100k random viewing angles to pick values. If retuning "how shiny," rerun that kind of sweep rather than eyeballing — the relationship between weight and visible saturation is non-linear (a 1.5x weight bump roughly doubled average reflection strength).
- `sunColor` uniform now tracks `LightingSystem.getSunColor()` live (pushed each frame in `TerrainGenerator.update()`) instead of a hardcoded near-white — reflections tint with the sun's actual current colour.

## Water / Sea — future options (not built beyond the shimmer above)
User noticed a large low/flat region reads as a black "sea" with the current palette, and asked whether it could move like water. Three tiers, cheapest to most expensive — only the first is built:

1. **Normal-perturbation shimmer** (✅ done, `TerrainMaterial.ts`) — reflection-only normal perturbation, time+position driven, gated by height. No geometry changes. Cheap because it reuses the `time` uniform and the existing reflection pipeline.
2. **Real vertex ripples** (not built — genuinely more work, plan only) — small time-based Y displacement in the vertex shader for low/flat vertices. Two real complications: (a) the terrain's normals are baked CPU-side at generation time (`geometry.computeVertexNormals()`) assuming undisplaced positions — a runtime vertex displacement needs ANALYTIC normal recomputation in-shader to keep lighting correct, not just a position offset; (b) `TerrainGrid.ts` is separate, static geometry draped on the SAME height data at generation time — if the surface mesh ripples in a vertex shader and the grid doesn't, the grid lines visibly detach/float above the moving surface. Doing this properly means replicating the identical displacement formula in both `TerrainMaterial.ts` and `EdgeMaterial.ts`'s vertex shaders. Moderate effort, touches vertex positions (not just constants) in both "Do Not Touch" shader files — plan it properly before starting, don't wing it.
3. **Dedicated water plane** (not built — the "do it properly" option, out of scope unless wanted) — separate mesh/material with scrolling normal maps, Fresnel reflectivity, maybe foam. Real per-game-engine water technique, most convincing result. The hard part isn't the shader, it's the SHAPE: the "sea" region isn't a fixed rectangle, it's whatever part of the region-masked flatland ends up below a height threshold, and that varies per seed/config — would need a generation-time mask (or a height-threshold clip in the water shader itself, sampling the terrain height texture) to know where to render. New technique investment, not a quick add.

## Do Not Touch (but see below — surgical numeric/defensive fixes are fine)
- `TerrainMaterial.ts` / `EdgeMaterial.ts` — fragile shader injection via `onBeforeCompile`; reflection and edge systems depend on precise uniform setup and injection order. **This means don't restructure the injection wiring or `#include` target strings without understanding them** — it does NOT mean the files are frozen. This session made several narrow, single-expression fixes here (a `max()` guard, `max`→`clamp`, a colour-tint uniform hookup) without incident. The bar: does the change touch WHAT gets matched/replaced and in what order, or just a constant/expression value within an already-matched block? The former needs care; the latter is normal maintenance.
- `LightingSystem.ts` — carefully tuned; colour transitions are parameter-driven. Same caveat as above — this session changed the sun's geometry type, added scanline shader code, and fixed a genuine below-horizon position bug, all as targeted edits.
- `BufferPool.ts` — used by TerrainGenerator; changes risk memory leaks
- `index.ts` — must remain a pure re-export with NO side effects (instantiating Game here caused the dual-instance bug)
- **Three.js reserved uniform names** — `cameraPosition` (and others: `viewMatrix`, `modelMatrix`, `projectionMatrix`, `normalMatrix`, etc.) are auto-declared by `#include <common>`/Three's own chunks and auto-populated every frame. Declaring your own uniform with one of these names in an `onBeforeCompile` injection is a GLSL redefinition — compile error. Hit this for real fixing the reflection view-direction bug (11 Aug 2026) — nearly shipped a custom `cameraPosition` uniform before catching it. If a shader needs "the camera," check whether Three already provides it before adding a custom one.

## HeightMap API (src/engine/terrain/HeightMap.ts)
All gameplay systems get terrain data via `terrainGenerator.getHeightMap()`. Available after first `generate()`, replaced on each `regenerate()` — **no change notification**, don't cache the reference across a regen.

| Method | Returns | Use for |
|---|---|---|
| `getHeightAt(x, z)` | `number` | Snap unit Y to surface |
| `getNormalAt(x, z)` | `Vector3` | Surface direction at a point |
| `getSlopeAngle(x, z)` | `number` (radians) | Traversability gate (0=flat, PI/2=cliff) |
| `isTraversable(x, z, maxSlope)` | `boolean` | Pathfinding walkability |
| `isInBounds(x, z)` | `boolean` | Distinguish "edge of map" from "off the map" (other queries clamp silently) |
| `isBuildable(x, z, footprintRadius, maxSlopeRad?)` | `boolean` | Placement check — stricter default slope tolerance than traversability |
| `getGroundedPosition(x, z)` | `Vector3` | Exact world pos on terrain surface |
| `getGroundOrientation(x, z, facingAngle)` | `Quaternion` | Unit tilt + heading combined |
| `getFlyingY(x, z, targetAlt, minClearance)` | `number` | Flying unit Y above terrain |

`getGroundOrientation` combines a slope-tilt quaternion (`up → surfaceNormal`) with a heading yaw. Units on slopes visually angle with the ground; flying units use `getFlyingY` to stay clear of peaks.

`GridSystem` also now has `worldToCell/cellToWorld/cellCenterWorld/getCellCount` — the logical placement grid, same cells `TerrainGrid.ts` draws.
